# US-021 — Set the duration of each booking slot per court

## Status

Done

## Objective

As an administrator, I want to set the duration of each booking slot per court.

## Functional description

This user story enables the administrator to set the duration of each booking slot per court. It belongs to EPIC-04 — Court Administration.

## Acceptance criteria

- [x] Set the duration of each booking slot per court is implemented and available to the administrator.
- [ ] The reservation is linked to a court, user, complex, and time range.
- [ ] Overlapping active reservations on the same court are prevented.
- [ ] Reservation is confirmed immediately for the MVP.
- [x] A court must have at least one active sport before it can accept reservations.
- [x] Availability rules define day of week, start/end time, and slot duration.
- [x] Business hours can be configured per complex.

> The unchecked reservation criteria are part of EPIC-06 (Reservations) and are not within the scope of this court-administration story.

## Business rules

- CRUD for `Court`.
- Association of one or more `Sport` to a court.
- `CourtAvailabilityRule` per day of week.
- `BusinessHours` per complex.
- Activation/deactivation of courts.
- Preparation for court-level time blocks.
- Two active reservations cannot overlap on the same court.

## Validations

- Validate required fields and data types server-side.
- Verify the court exists and is active.
- Verify the slot is not already reserved.
- Apply the policy configured for the reservation's complex, with global `CancellationPolicy` values as fallback, for cancel operations.
- Return clear, structured error messages for invalid input.

## Error cases

- Invalid or missing input data.
- User is not authenticated or authorized.
- The referenced resource does not exist.
- The requested slot is no longer available.
- The court is inactive.

## Security considerations

- Authenticate and authorize every mutating request.
- Do not expose internal implementation details in error responses.
- Avoid logging sensitive data such as passwords, tokens, or PII.

## Technical notes

- `Court`: `Id`, `SportsComplexId`, `Name`, `Description`, `SurfaceType`, `Indoor`, `Status`, `CreatedAt`, `UpdatedAt`.
- `CourtSport` many-to-many join table.
- `CourtAvailabilityRule`: `CourtId`, `DayOfWeek`, `StartTime`, `EndTime`, `SlotDurationMinutes`, `IsActive`.
- Validate `StartTime < EndTime` and that slots fit within the range.
