# US-083 — Configure a sports complex timezone

## Status

Ready

## Objective

As a complex administrator, I want to configure the IANA timezone of my sports complex so that business hours, court availability, and reservations are calculated correctly for the complex location, including daylight-saving-time changes.

## Functional description

The current fixed `UtcOffsetMinutes` setting is insufficient because a UTC offset can change by date in locations that observe daylight saving time. This story introduces an IANA timezone identifier owned by the sports complex, such as `America/Montevideo`, `America/Argentina/Buenos_Aires`, or `America/New_York`.

The complex timezone is the source of truth for calculating availability. A visitor's browser timezone is used only to format the returned UTC timestamps for display.

## Acceptance criteria

- [ ] A sports complex persists an IANA `TimeZoneId` and new complex creation requires a valid value.
- [ ] A complex administrator can view and update the timezone through a searchable, human-readable timezone selector; administrators do not enter UTC offsets manually.
- [ ] The API accepts and returns the complex `TimeZoneId` for authorized administration flows.
- [ ] The public availability endpoint derives the UTC interval from the complex timezone and selected complex-local date; it does not use a caller-provided UTC offset.
- [ ] Availability rules and business hours continue to represent local wall-clock time at the complex.
- [ ] Availability slots are returned as UTC instants and displayed in the viewer's browser-local timezone.
- [ ] A visitor whose browser timezone differs from the complex timezone sees the correct instant converted to their own local time.
- [ ] Availability is correct on dates before and after daylight-saving-time offset changes for a DST-observing complex timezone.
- [ ] Invalid local times during a daylight-saving-time spring-forward transition are not offered as slots.
- [ ] Ambiguous local times during a daylight-saving-time fall-back transition use a documented, deterministic policy.
- [ ] Existing complexes are migrated without silently treating a fixed UTC offset as an equivalent IANA timezone; complexes with an unresolved timezone require administrator review before public availability is calculated.
- [ ] `UtcOffsetMinutes` is removed from the complex contract, domain model, persistence model, frontend forms, and availability API only after `TimeZoneId` is fully adopted.
- [ ] Unit, integration, frontend, and E2E tests cover the timezone behavior.

## Business rules

1. A sports complex owns exactly one IANA timezone identifier.
2. `BusinessHours` and `CourtAvailabilityRule` values represent times local to the sports complex.
3. Reservations, court blocks, and returned availability slots remain UTC instants.
4. The complex timezone determines the UTC instant for a selected complex-local date and local wall-clock time.
5. A user's browser timezone must not influence which slots are available.
6. The public frontend formats returned UTC slots in the viewer's local timezone and must clearly indicate that displayed times are local to the viewer.
7. An IANA timezone identifier must be supported by the deployed .NET runtime.

## Validations

- Validate that `TimeZoneId` is non-empty, within the configured maximum length, and resolvable by `TimeZoneInfo` in the application runtime.
- Reject malformed, unsupported, or deprecated timezone identifiers with a structured validation error.
- Validate complex ownership and `ComplexAdmin` authorization before a timezone can be changed.
- Validate the selected availability date and court as today.
- Detect invalid and ambiguous local times when resolving a rule or business-hours interval for a selected date.
- Prevent public availability calculation for a complex whose migrated timezone remains unresolved.

## Error cases

| Scenario | Expected behavior |
|---|---|
| Unsupported or malformed `TimeZoneId` | `400 Bad Request` with a validation error. |
| Caller is not a complex administrator | `401 Unauthorized` or `403 Forbidden`, consistent with existing authorization behavior. |
| Complex does not exist or does not belong to the caller | `404 Not Found` or `403 Forbidden`, consistent with existing multi-tenancy behavior. |
| Existing complex has no resolved timezone | Public availability returns a clear unavailable/configuration response without inventing an offset. |
| Local rule interval contains a DST spring-forward gap | Invalid local times are excluded from the generated slots. |
| Local rule interval contains a DST fall-back overlap | Slots follow the documented deterministic overlap policy. |

## Security considerations

- Only authorized complex administrators may change a complex timezone.
- A caller must not supply a timezone or UTC offset to influence another complex's availability calculation.
- Preserve existing complex ownership and multi-tenancy checks.
- Do not disclose internal persistence or runtime details in validation errors.
- Do not log access tokens, user PII, or reservation notes while diagnosing timezone resolution errors.

## Technical notes

- Replace the fixed `SportsComplex.UtcOffsetMinutes` model with a `TimeZoneId` model using IANA identifiers.
- Use `TimeZoneInfo` to resolve the complex-local date and local availability/business-hours times to UTC instants for the specific date.
- The availability endpoint remains `GET /api/v1/complexes/{complexId}/availability?courtId=&date=`. Remove the `utcOffsetMinutes` query parameter after a compatible API migration plan is agreed.
- Preserve UTC storage for `Reservation.StartAt`, `Reservation.EndAt`, `CourtBlock.StartAt`, and availability response timestamps.
- Add an EF Core migration for the new column and a data-migration strategy that distinguishes known timezone assignments from unresolved existing configurations.
- Verify IANA identifier support on both the Windows development environment and the deployed Linux/container runtime.
- The administrator selector should use an approved timezone list or runtime-supported list with search; it must not expose the reversed `Date.getTimezoneOffset()` sign convention.
- Review reservation creation, recurring reservations, cancellation windows, court blocks, admin calendars, and public availability for fixed-offset assumptions.

## Tests required

### Unit

- `SportsComplex` accepts valid IANA timezone identifiers and rejects invalid identifiers.
- Availability generation resolves a non-DST timezone, such as `America/Montevideo`, to correct UTC slot instants.
- Availability generation resolves a DST-observing timezone, such as `America/New_York`, before and after an offset change.
- Slot generation excludes nonexistent local times during a spring-forward transition.
- Slot generation follows the documented policy for ambiguous fall-back local times.
- A visitor timezone does not affect the backend's generated UTC slots.

### Integration

- Complex creation and update persist a valid `TimeZoneId`.
- Invalid timezone identifiers return a validation error.
- The availability endpoint returns correct UTC slot instants for a complex whose timezone differs from the caller/browser timezone.
- The availability endpoint does not accept or rely on `utcOffsetMinutes`.
- Existing complexes without a resolved timezone follow the approved unavailable/configuration behavior.
- Reservation creation and court blocks continue to use the same UTC instants derived from the complex timezone.

### Frontend

- The complex-profile form renders, selects, validates, and saves an IANA timezone.
- The public complex detail page requests availability without a browser-derived UTC offset.
- Returned UTC slot timestamps are rendered in the browser-local timezone.
- The UI communicates the timezone used for displayed availability.

### E2E

- An administrator configures a timezone for a complex.
- A visitor in a different browser timezone sees the correct converted slots.
- A DST boundary scenario is covered in a controlled test environment.

## Out of scope

- Automatic geocoding or timezone inference from an address or latitude/longitude.
- Changing the timezone of historical reservation timestamps.
- Supporting a different timezone per court within a complex.
- Calendar synchronization with external providers.
