# US-079 — Search and select a user when creating a manual reservation

## Status

Ready

## Objective

As an administrator, I want to search and select a user when creating a manual reservation so that I can quickly find the correct account by email, name, or phone number.

## Functional description

This user story improves the manual reservation form in the admin panel by replacing the plain `UserID` input with an autocomplete and a dedicated "Search User" option. It belongs to EPIC-06 — Reservations.

## Acceptance criteria

- [ ] The manual reservation form renders a `UserID` autocomplete instead of a raw text input.
- [ ] The autocomplete suggests users as the administrator types.
- [ ] Autocomplete results can be matched by `Email`, `FullName`, or `PhoneNumber`.
- [ ] Each suggestion displays enough context (e.g., full name and email) to identify the correct user.
- [ ] A "Search User" button is available next to the autocomplete.
- [ ] Clicking "Search User" opens a search dialog where the administrator can search by email, name, and phone number.
- [ ] Selecting a user from the autocomplete or the search dialog populates the `UserID` field.
- [ ] The selected user is validated before the reservation can be submitted.
- [ ] Only authenticated and authorized administrators can use the search.
- [ ] Results are scoped to the current complex when multi-tenancy requires it.
- [ ] Empty and no-results states are handled clearly.

## Business rules

- Manual reservations are created by administrators on behalf of users.
- Search matches support partial input on email, full name, and phone number.
- Phone number search should account for normalized values where possible.
- Search results must not expose sensitive or unnecessary user data.
- A minimum query length (e.g., 3 characters) may be required before searching.
- Multi-tenancy: administrators can only search users within the scope of their complex.

## Validations

- `UserID` is required to create a manual reservation.
- The selected user must exist and be active.
- Search input must be validated for length and allowed characters.
- Administrators must be authorized for the target complex.

## Error cases

- No users match the search query.
- Search query is too short or contains invalid characters.
- User is not authenticated or authorized.
- Search service is unavailable.
- Selected user is blocked or inactive.

## Security considerations

- Authorize every search and autocomplete request.
- Do not expose PII beyond what is needed for user selection.
- Rate limit the search endpoint to prevent abuse.
- Sanitize and validate search input to prevent injection attacks.
- Avoid logging PII such as email or phone numbers.

## Technical notes

- `User` entity fields: `Id`, `Email`, `FullName`, `PhoneNumber`, `Status`.
- Add or reuse an admin search endpoint, e.g., `GET /api/admin/users/search?query={value}&sportsComplexId={id}`.
- Frontend components: `UserAutocomplete`, `UserSearchDialog`.
- The existing manual reservation form from US-034 should be updated to integrate the new controls.
- Debounce autocomplete requests to avoid excessive backend calls.
- Multi-tenancy key: `SportsComplexId`.

## Tests required

- **Unit**: `UserAutocomplete` filtering and selection behavior.
- **Integration**: search endpoint returns correct, scoped results.
- **E2E**: administrator searches for a user by email, name, and phone number and creates a manual reservation.

## Out of scope

- Creating a new user from the reservation form.
- Bulk user import or advanced filters.
- Public user search.

## Dependencies
