# US-029 — Create a reservation for an available slot

## Status

Done

## Objective

As a user, I want to create a reservation for an available slot.

## Functional description

This user story enables the user to create a reservation for an available slot. It belongs to EPIC-06 — Reservations.

## Acceptance criteria

- [x] Create a reservation for an available slot is implemented and available to the user.
- [x] Required fields are validated before persistence.
- [x] The created resource is persisted and returned with an identifier.
- [x] Only authenticated and authorized users can create the resource.
- [x] Timestamps `CreatedAt` and `UpdatedAt` are tracked.
- [x] A reservation is linked to a court, a user, a complex, and a time range.
- [x] Admins can cancel any reservation in their complex and record a reason.

## Business rules

- Create a single reservation.
- Query reservation details.
- List user's reservations.
- List complex reservations for admins.
- Cancel reservations.
- Manual reservation creation by admins.
- Conflict prevention (no overlapping active reservations).
- Mark reservation as completed or no-show.
- Basic reservation history.
- Input validation must be enforced on the server, not only the client.
- Only authorized users can modify resources they own or administer.

## Validations

- Validate required fields and data types server-side.
- Enforce length, format, and range limits.
- Check uniqueness where applicable.
- Verify the actor has permission to create or update the resource.
- Return clear, structured error messages for invalid input.

## Error cases

- Invalid or missing input data.
- User is not authenticated or authorized.
- The referenced resource does not exist.
- Duplicate or conflicting data violates uniqueness rules.

## Security considerations

- Authenticate and authorize every mutating request.
- Do not expose internal implementation details in error responses.
- Avoid logging sensitive data such as passwords, tokens, or PII.
- Sanitize and validate all user input to prevent injection attacks.

## Technical notes

- `Reservation` entity: `Id`, `SportsComplexId`, `CourtId`, `UserId`, `StartAt`, `EndAt`, `Status`, `Source`, `RecurringReservationId`, `Notes`, `CreatedAt`, `UpdatedAt`, `CancelledAt`, `CancellationReason`.
- Status values: `Pending`, `Confirmed`, `CancelledByUser`, `CancelledByAdmin`, `Completed`, `NoShow`.
- For the MVP, reservations made by users are auto-confirmed.
- User cancellation policy is resolved per complex through US-075, with the global `CancellationPolicy` configuration as fallback. Administrative cancellation is not governed by the user cancellation deadline.
- Concurrency protection: serializable transaction or advisory lock per `(CourtId, StartAt)`.
