# US-010 — The system to distinguish user, complex admin, and super admin roles

## Status

Ready

## Objective

As an administrator, I want the system to distinguish user, complex admin, and super admin roles so features are protected.

## Functional description

This user story covers the system to distinguish user, complex admin, and super admin roles for the administrator. The goal is that features are protected. It belongs to EPIC-02 — Identity and Access.

## Acceptance criteria

- [ ] The system to distinguish user, complex admin, and super admin roles is implemented and available to the administrator.
- [ ] The system distinguishes `User`, `ComplexAdmin`, and `SuperAdmin` roles.
- [ ] Roles are enforced in both UI and API.
- [ ] Complex-scoped endpoints reject admins from other complexes.
- [ ] The JWT contains user id, email, name, and roles.
- [ ] `User`, `ComplexAdmin`, and `SuperAdmin` roles are enforced in UI and API.

## Business rules

- Google OpenID Connect integration.
- JWT issuance and validation.
- User profile completion with mandatory phone number.
- Roles and authorization policies.
- Protected routes and endpoints.
- Preparation for future phone verification.

## Validations

- Validate required fields and data types server-side.
- Return clear, structured error messages for invalid input.

## Error cases

- Invalid or missing input data.
- User is not authenticated or authorized.
- The referenced resource does not exist.

## Security considerations

- Authenticate and authorize every mutating request.
- Do not expose internal implementation details in error responses.
- Avoid logging sensitive data such as passwords, tokens, or PII.
- Enforce role checks on both the API and the UI routing layer.
- Verify the actor belongs to or administers the affected complex.

## Technical notes

- Use ASP.NET Core `AddJwtBearer` and Google authentication.
- Store `GoogleSubjectId`, `Email`, `FullName`, `PhoneNumber`, and `PhoneVerified`.
- Custom `IAuthorizationRequirement` for complex-scoped access.
- Frontend stores access token in memory and refresh token in `HttpOnly` cookie if implemented.
