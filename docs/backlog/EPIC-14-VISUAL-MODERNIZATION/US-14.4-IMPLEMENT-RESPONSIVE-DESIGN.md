# US-14.4 — Implement Responsive Design

## Status

Proposed — awaiting human review.

## Objective

As a MOVA user, I want to use the platform across different screen sizes, so that I can search for and book sports facilities from desktop, tablet, or mobile devices.

## Functional description

Establish a mobile-first responsive baseline for the visual-modernization scope: public landing content, its header, hero, carousel, primary CTAs, and reusable visual components. Existing functional workflows must remain usable at supported viewport sizes.

## Acceptance criteria

- [ ] Given a user opens the public experience on a mobile viewport, when landing-page sections render, then text, CTAs, cards, and navigation fit without unintended horizontal scrolling.
- [ ] Given a user opens the same experience on tablet, laptop, or desktop, when the viewport changes, then layout, spacing, and content hierarchy adapt appropriately.
- [ ] Given a primary action is rendered on a touch-oriented viewport, when a user taps it, then it has an adequately usable target and remains distinguishable.
- [ ] Given content is resized or zoomed, when the user reaches the responsive layout, then essential content and controls remain visible and operable.
- [ ] Given an existing public CTA is used at any supported size, when navigation completes, then its existing behavior is unchanged.

## Business rules

- The platform remains mobile-first and responsive without changing underlying business logic.
- Current routes, user journeys, and authorization behavior are preserved.
- Responsive changes apply to the Epic 14 visual scope and must not require redesigning unrelated feature pages.

## Validations

- Verify public home content has no unintended horizontal overflow at the chosen mobile baseline.
- Verify key layout changes at mobile, tablet, laptop, and desktop viewports.
- Verify tap targets, focus states, and readable line lengths remain usable.

## Error cases

- If content becomes longer due to localization, the layout must wrap or reflow rather than hide required labels or actions.

## Security considerations

- Responsive styling must not expose routes, controls, or account data that existing authorization rules hide.
- No API, authentication, authorization, or data-model change is included.

## Technical notes

- Affected area: shared MUI theme, `HomePage`, `HomeFeaturedSection`, `AppHeader`, and the components created by related Epic 14 stories.
- Existing code uses MUI breakpoint objects in `sx` props; standardize and reuse that approach rather than introduce a separate CSS framework.
- The exact viewport matrix is a review decision; validate at least one representative size for each epic-specified device class.

## Technical subtasks

- **TASK-14.4.1 — Define responsive component rules**: Establish mobile-first spacing, grid, typography, and CTA rules using approved tokens. **Done when:** shared rules can be applied consistently. **Testing:** theme/component-level review. **Dependencies:** US-14.5. **Sequence:** BLOCKING.
- **TASK-14.4.2 — Adapt public landing components**: Apply responsive rules to the hero, carousel, header, section grids, cards, and CTA groups. **Done when:** public landing content reflows without overflow. **Testing:** component tests and manual viewport matrix. **Dependencies:** US-14.1, US-14.2, US-14.3, TASK-14.4.1. **Sequence:** BLOCKING.
- **TASK-14.4.3 — Add responsive regression coverage**: Capture high-value mobile and desktop behavior for responsive components. **Done when:** regressions in required actions or layouts are detected. **Testing:** Vitest component tests and Playwright only where existing E2E configuration makes it practical. **Dependencies:** TASK-14.4.2. **Sequence:** BLOCKING.

## Tests required

- **Component:** CTA and required navigation controls remain present in mobile and desktop render paths.
- **Manual responsive:** test representative mobile, tablet, laptop, and desktop widths, including longer localized labels and browser zoom.

## Out of scope

- Native mobile applications, offline support, device-specific booking features, or redesign of all authenticated feature pages.
- Changes to backend APIs, booking rules, authentication, authorization, or data storage.

## Dependencies

- US-14.1 — Modernize the Hero Section.
- US-14.2 — Implement a Sports Image Carousel.
- US-14.3 — Improve Main Navigation.
- US-14.5 — Create a Reusable Visual Design System.

## Definition of Done

- All acceptance criteria pass at the approved viewport matrix.
- Relevant frontend tests, linting, and build pass.
- No public navigation or CTA regression is introduced.
- Human review approval is obtained before implementation.
