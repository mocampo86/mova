# US-058 — Rate limiting on login and reservation endpoints

## Status

Ready

## Objective

As a security owner, I want rate limiting on sensitive authentication and reservation endpoints so that the application is protected against brute-force attempts, automated abuse, and excessive request traffic.

## Functional description

Implement rate limiting on sensitive API endpoints, specifically authentication/login and reservation creation.

Rate limits must be applied per client or authenticated user as appropriate, without unnecessarily limiting unrelated API endpoints.

When a client exceeds the configured limit, the API must reject additional requests with HTTP `429 Too Many Requests` and return a clear, structured error response.

This user story belongs to EPIC-10 — Audit and Operations.

## Acceptance criteria

* [ ] Sensitive authentication/login endpoints have rate limiting configured.
* [ ] Reservation creation endpoints have rate limiting configured.
* [ ] Authentication rate limiting uses an appropriate client partitioning strategy, such as the effective client IP.
* [ ] Reservation creation rate limiting uses the authenticated user ID as the primary partition key when available.
* [ ] Rate limits are configurable and are not hardcoded throughout the application.
* [ ] Requests within the configured limit are processed normally.
* [ ] Requests exceeding the configured limit return HTTP `429 Too Many Requests`.
* [ ] Rate-limit responses use the API's standard structured error format.
* [ ] A `Retry-After` header is returned when the retry delay can be determined.
* [ ] Rate limiting does not unintentionally affect unrelated endpoints.
* [ ] Existing authentication and reservation flows continue to work normally when clients remain within the configured limits.
* [ ] Rate limiting works correctly when the application is deployed behind the project's configured proxy/load balancer.

## Business rules

* Login/authentication endpoints must be protected against excessive requests and automated abuse.
* Reservation creation must be protected against excessive requests from the same authenticated user.
* Rate limits must be configurable per endpoint/policy.
* Different users must not unintentionally share the same reservation rate-limit quota.
* Authentication rate limiting must not trust arbitrary client-supplied forwarding headers.
* Existing authentication, authorization, and reservation business rules remain unchanged.

## Validations

* Determine the correct partition key before applying a rate-limit policy.
* For authentication requests, use the effective client IP according to the application's trusted proxy/forwarded-header configuration.
* For authenticated reservation requests, use the authenticated user ID when available.
* Preserve existing request validation, authentication, and authorization behavior.
* Return clear and structured responses when the rate limit is exceeded.

## Error cases

### Rate limit exceeded

Return:

`429 Too Many Requests`

using the API's standard error response format.

Example:

```json
{
  "error": "rate_limit_exceeded",
  "message": "Too many requests. Please try again later."
}
```

Include `Retry-After` when supported by the configured limiter.

### Unauthenticated reservation request

Existing authentication behavior must remain unchanged.

Rate limiting must not replace authentication or authorization checks.

### Invalid request

Existing validation behavior must remain unchanged.

## Security considerations

* Do not expose internal rate-limiter implementation details in API responses.
* Do not log passwords, authentication tokens, JWTs, refresh tokens, or other sensitive credentials.
* Do not use untrusted forwarding headers directly to determine the client identity.
* Ensure proxy/forwarded-header handling is compatible with the production deployment configuration.
* Prevent one authenticated user from consuming another user's reservation quota.
* Rate limiting is an additional protection and must not replace authentication, authorization, or existing reservation validation.

## Technical notes

Use ASP.NET Core `RateLimiting` middleware.

Prefer named policies so authentication and reservation endpoints can have different configurations.

Conceptually:

```text
Authentication endpoint
        ↓
Effective client IP
        ↓
Authentication rate-limit policy
        ↓
Allowed → authentication flow
Exceeded → 429
```

For reservations:

```text
Authenticated user
        ↓
User ID
        ↓
Reservation rate-limit policy
        ↓
Allowed → reservation creation
Exceeded → 429
```

Rate-limit values should be configurable through the application's configuration system, such as `appsettings.json` and environment-specific configuration, rather than being scattered as hardcoded values.

Example configuration structure:

```json
{
  "RateLimiting": {
    "Authentication": {
      "PermitLimit": 10,
      "WindowSeconds": 60
    },
    "ReservationCreation": {
      "PermitLimit": 20,
      "WindowSeconds": 60
    }
  }
}
```

The exact limits must follow existing project requirements or configuration. If no limits have been defined, document the selected defaults and rationale.

When deployed behind Azure or another reverse proxy/load balancer, ensure the application derives the effective client IP only from trusted proxy configuration.

## Tests required

### Unit

* Rate-limit configuration is correctly loaded and validated where applicable.
* Partition-key selection behaves correctly.
* Authenticated reservation requests are partitioned by user ID.

### Integration

* Authentication requests within the configured limit succeed normally.
* Authentication requests exceeding the configured limit return `429`.
* Reservation creation requests within the configured limit reach the existing reservation flow normally.
* Reservation creation requests exceeding the configured limit return `429`.
* Different authenticated users have independent reservation quotas.
* Rate limiting one user does not block another user.
* Unrelated endpoints are not unintentionally rate limited.
* Rate-limit responses follow the API's structured error format.
* `Retry-After` is returned when available.
* Existing authentication and reservation behavior remains unchanged within allowed limits.

### E2E

E2E coverage is required only if frontend behavior changes as part of handling `429` responses.

If the frontend already handles structured API errors generically and no UI changes are necessary, backend integration coverage is sufficient.

## Out of scope

* Reimplementing Google OpenID Connect authentication.
* Changing JWT generation or JWT claims.
* Implementing or modifying refresh-token behavior unless required for the rate-limited endpoint.
* Implementing health-check endpoints.
* Implementing audit logging.
* Implementing backup or recovery procedures.
* Changing reservation conflict or availability rules.
* Global rate limiting for every API endpoint.
* CAPTCHA or advanced bot-detection systems.
* Distributed/global rate limiting infrastructure unless required by the current deployment architecture.
* Advanced DDoS protection provided by external infrastructure.
