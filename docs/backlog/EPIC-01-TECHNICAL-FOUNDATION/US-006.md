# US-006 — Health Checks

## Objective

As an operator, I want health checks exposed so orchestrators can monitor the API.

## Functional description

Add ASP.NET Core health checks to the API. Provide separate liveness and readiness endpoints; liveness should only indicate the process is running, while readiness should verify critical dependencies such as the database.

## Acceptance criteria

- [ ] A liveness endpoint (for example, `/health/live`) returns healthy when the application is running.
- [ ] A readiness endpoint (for example, `/health/ready`) returns healthy only when critical dependencies are reachable.
- [ ] A database health check is registered and used by the readiness endpoint.
- [ ] Health responses use JSON with status and optional dependency details.
- [ ] Healthy responses return HTTP 200; unhealthy responses return HTTP 503.
- [ ] Health endpoints do not require authentication.
- [ ] Health endpoints are lightweight and do not perform heavy operations.

## Business rules

- Liveness checks must not depend on external services.
- Readiness checks must verify critical dependencies needed to serve traffic.
- Health endpoints must not expose sensitive details.

## Validations

- Call `/health/live` and verify HTTP 200 with a healthy status.
- Call `/health/ready` with the database up and verify HTTP 200.
- Stop PostgreSQL and verify `/health/ready` returns HTTP 503.
- Verify the response schema.

## Error cases

- Database is unavailable.
- A health check implementation throws an exception.
- Authentication middleware blocks the health endpoint.

## Security considerations

- Do not expose detailed diagnostics, connection strings, or internal state.
- Limit health check detail output in production.
- Consider rate limiting if the endpoint is public.

## Technical notes

- Use ASP.NET Core Health Checks middleware.
- Register a `DbContext` health check or a custom database ping.
- Map endpoints with `MapHealthChecks` and set response writers.

## Tests required

- **Integration**: health endpoints return the correct status in healthy and unhealthy states.
- **Unit**: health check registration and response formatting.

## Out of scope

- Custom probes for external services beyond the database.
- Kubernetes probe manifest configuration.

## Dependencies

- US-001 — Runnable .NET Solution.
- US-003 — PostgreSQL Local Setup with Docker Compose.

## Definition of Done

- Liveness and readiness endpoints are exposed.
- Database readiness check works.
- Tests pass and code review is approved.
