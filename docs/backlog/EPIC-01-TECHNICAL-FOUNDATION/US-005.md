# US-005 — Structured Logging and Global Exception Handling

## Status

Ready

## Objective

As an operator, I want structured logging and global exception handling so I can diagnose issues.

## Functional description

Configure Serilog for the backend to produce structured logs, add a global exception handler middleware that converts unhandled exceptions into a standardized error response, and set up structured console logging for the frontend. Ensure no sensitive data is written to logs.

## Acceptance criteria

- [ ] Serilog is configured in the backend with structured console output.
- [ ] Logs include at minimum timestamp, log level, request path, request ID, and message.
- [ ] A global exception handler middleware catches unhandled API exceptions.
- [ ] The API returns a consistent error response contract (status code, error code, message, optional trace ID).
- [ ] Stack traces and internal details are hidden in non-development environments.
- [ ] The frontend has a structured console logging setup.
- [ ] No secrets, tokens, passwords, or PII are logged.

## Business rules

- Unhandled exceptions must not crash the process.
- Error responses must not leak stack traces or internal implementation details in production.
- Logs must be structured and filterable by level and correlation ID.

## Validations

- Trigger an unhandled exception in development and verify the log and response.
- Run the API in a production-like environment and confirm stack traces are not returned.
- Scan logs for sensitive strings.

## Error cases

- An unhandled exception occurs in a controller or service.
- The exception handler itself throws an exception.
- A logging sink becomes unavailable.

## Security considerations

- Sanitize or redact sensitive fields from log output.
- Do not log request bodies that may contain passwords or tokens.
- Control log levels per environment to reduce information disclosure.

## Technical notes

- Use Serilog with enrichers for request paths and correlation IDs.
- Use ASP.NET Core `IExceptionHandler` or custom middleware for global handling.
- Keep the error response contract consistent with `docs/api/ERROR-CONTRACT.md`.

## Tests required

- **Unit**: error response builder and log redaction logic.
- **Integration**: middleware returns the expected response for thrown exceptions.
- **E2E**: frontend shows a generic error state when an API error occurs.

## Out of scope

- Centralized log aggregation (ELK, Loki, etc.).
- Alerting or incident management integration.

## Dependencies

- US-001 — Runnable .NET Solution.
- US-002 — React Application Scaffold.

## Definition of Done

- Structured logging is configured.
- Global exception handling returns consistent responses.
- No sensitive data is logged.
- Tests pass and code review is approved.

Backend API and frontend application.
