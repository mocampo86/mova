# US-004 — Environment Configuration and Secret Management

## Status

Done

## Objective

As a developer, I want environment-based configuration and secret management so production credentials are never committed.

## Functional description

Set up ASP.NET Core configuration with `appsettings.json`, environment-specific overrides, User Secrets for local development, and environment variables for deployed environments. Bind settings to strongly-typed options classes and validate required values at startup.

## Acceptance criteria

- [x] Non-sensitive defaults live in `appsettings.json`.
- [x] Local non-sensitive overrides live in `appsettings.Development.json`.
- [x] Sensitive local values are stored in .NET User Secrets.
- [x] Production and staging secrets are loaded from environment variables or a secret manager.
- [x] `.gitignore` excludes `.env`, `secrets.json`, and environment-specific files that may contain secrets.
- [x] Settings are bound to strongly-typed options classes.
- [x] Required configuration is validated at startup; the application fails fast with a clear error when missing.
- [x] A repository scan confirms no secrets are present in source control.

## Business rules

- Secrets must never be committed to source control.
- Configuration hierarchy must be: environment variables > User Secrets > `appsettings.Development.json` > `appsettings.json`.
- Required settings must be validated early at application startup.

## Validations

- Search the repository for connection strings, passwords, API keys, and tokens.
- Run the API locally and verify it loads configuration without errors.
- Verify `.gitignore` excludes sensitive files.

## Error cases

- A required configuration key is missing at startup.
- A configuration value is malformed or invalid.
- A secret is accidentally committed and must be rotated.

## Security considerations

- Rotate any credentials exposed in source control.
- Use a secret manager (for example, Azure Key Vault) in production; local User Secrets are only for development.
- Audit git history for leaked secrets if a rotation is needed.

## Technical notes

- Use ASP.NET Core configuration providers and the Options pattern.
- Validate options with `ValidateDataAnnotations` or custom validation.
- Keep `appsettings.Production.json` out of source control if it contains environment-specific values.

## Tests required

- **Unit**: options validation behavior.
- **Integration**: configuration binding and validation at startup.

## Out of scope

- Production integration with a specific cloud secret manager.
- Certificate and encryption key management.

## Dependencies

- US-001 — Runnable .NET Solution.
- US-003 — PostgreSQL Local Setup with Docker Compose (connection string uses config).

- No secrets are in source control.
- Validation fails fast with clear messages.
- Tests pass and code review is approved.
