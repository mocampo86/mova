# US-074 — Cancel an upcoming reservation from the user dashboard

## Status

Ready

## Objective

As a user, I want to cancel an upcoming reservation from my reservations page so that the time slot becomes available again and the cancellation is recorded.

## Functional description

This user story provides the frontend UI for `US-032`. It adds a cancel action to each upcoming reservation on `/user/reservations` and a confirmation dialog where the user can optionally enter a reason. The page then calls the user cancel endpoint and refreshes the list and availability data.

## Acceptance criteria

- [ ] The upcoming reservations page shows a cancel button for each `Pending` or `Confirmed` reservation.
- [ ] Clicking cancel opens a confirmation dialog with an optional reason field.
- [ ] Confirming the cancellation calls `PATCH /api/v1/users/me/reservations/{id}/cancel`.
- [ ] After a successful cancellation the upcoming reservations list and reservation history are refreshed.
- [ ] Court availability queries are invalidated so the freed slot can be booked again.
- [ ] The dialog disables the confirm button while the mutation is pending and closes on success.
- [ ] Errors (including `CANCELLATION_DEADLINE_PASSED`) are surfaced to the user.
- [ ] Cancelled reservations are no longer shown in the upcoming list and move to the history list.

## Business rules

- A user can only cancel reservations they own.
- A user can only cancel reservations that are `Pending` or `Confirmed`.
- User cancellations are subject to the policy configured for the reservation's complex; global `CancellationPolicy` values are used as fallback.
- The effective policy is resolved from the reservation's complex; the global `CancellationPolicy` configuration is used as fallback.
- The freed slot becomes available immediately after cancellation.

## Validations

- Validate the user is authenticated.
- Validate the reservation belongs to the current user.
- Validate the cancellation deadline has not passed.

## Error cases

- User is not authenticated or authorized.
- The reservation does not exist or is not owned by the user.
- The cancellation deadline has passed (`CANCELLATION_DEADLINE_PASSED`).
- The reservation is already cancelled, completed, or no-show.

## Security considerations

- Authenticate and authorize every request.
- Do not expose internal implementation details in error responses.
- Avoid logging sensitive data such as tokens or PII.
