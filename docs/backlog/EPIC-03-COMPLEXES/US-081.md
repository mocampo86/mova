# US-081 — Ensure atomic onboarding for complex creation

## Status

Ready

## Objective

As a system, I want the creation of a sports complex and its initial configuration to be an atomic operation, so that the complex is never left in a partially persisted state when any step of the onboarding fails.

## Description / Context

This user story resolves the finding where `CreateComplexHandler` and `CompleteComplexAdminHandler` persist the `SportsComplex`, the `ComplexAdministrator` relationship, and the user role in one database save, and then create and persist the default `BusinessHours` records in a separate, later save. If the second save fails, the system retains a complex and administrator association without the operational defaults that the creation logic intended to establish.

The goal is to ensure that complex creation and onboarding are treated as a single logical, transactional unit: either the `SportsComplex`, the `ComplexAdministrator`, the user role, and the default business hours are all persisted together, or none of them are.

## Acceptance criteria

- [ ] The creation of a `SportsComplex`, its first `ComplexAdministrator`, the user role assignment, and the default `BusinessHours` records are executed within a single unit of work / transaction.
- [ ] The transaction is committed only after all required onboarding steps complete successfully.
- [ ] If any step fails, the transaction is rolled back and no partial records remain in the database.
- [ ] A caller that retries creation after a transient failure does not produce duplicate `SportsComplex`, `ComplexAdministrator`, `BusinessHours`, or user role records.
- [ ] The initial status of the complex (`Active` for direct creation, `Pending` for complex-admin onboarding) is preserved on success.
- [ ] Exceptions during the onboarding are propagated to the caller and logged through the existing logging mechanism.
- [ ] The behavior is covered by unit, integration, and, where applicable, end-to-end tests.

### Given / When / Then

**Scenario 1: Successful complex creation persists everything atomically**

- **Given** an authenticated user provides valid complex information.
- **When** the system creates the complex, links the first administrator, grants the role, and generates the default business hours.
- **Then** all records are committed together, the complex is in the expected initial status, the administrator can access the complex, and the default business hours exist for every day of the week.

**Scenario 2: Failure during default business hours creation rolls back everything**

- **Given** the complex, administrator, and role have been added to the current unit of work.
- **When** the generation or persistence of the default business hours throws an exception.
- **Then** the entire transaction is rolled back, no `SportsComplex`, `ComplexAdministrator`, or user role records remain persisted, and the caller receives a failure response.

**Scenario 3: Failure during administrator or role assignment rolls back everything**

- **Given** the complex has been added to the current unit of work.
- **When** the creation of the `ComplexAdministrator` or the user role assignment throws an exception.
- **Then** the transaction is rolled back, no partial complex record remains, and the caller receives a failure response.

**Scenario 4: Retry after transient failure does not create duplicates**

- **Given** a previous onboarding attempt failed and was fully rolled back.
- **When** the caller retries with the same valid input.
- **Then** a single `SportsComplex`, a single `ComplexAdministrator`, a single set of user roles, and a single set of default business hours are created.

**Scenario 5: Onboarding preserves the intended initial status**

- **Given** the direct complex creation path defaults the complex to `Active` and the complex-admin onboarding path defaults it to `Pending`.
- **When** the transaction completes successfully.
- **Then** the complex is persisted with the intended status for each path.

## Business rules

1. Complex creation and its initial configuration are a single logical, indivisible operation.
2. The database must never contain a `SportsComplex` or `ComplexAdministrator` record without the corresponding default business hours.
3. The initial status of the complex is determined by the creation path (`Active` for direct creation, `Pending` for onboarding) and must be respected within the transaction.
4. Retry safety must be provided by the natural constraints of the system (unique indexes, idempotent design, or explicit duplication checks).
5. Partial failures must not be visible to other concurrent callers or subsequent operations.
6. The behavior must not affect the public active-only visibility rules or the super-admin moderation workflow.

## Technical considerations

- Use the existing `IUnitOfWork` abstraction or an EF Core explicit transaction to wrap the full onboarding sequence.
- Add all entities (`SportsComplex`, `ComplexAdministrator`, user role, default `BusinessHours` for each `DayOfWeek`) to the same `DbContext` change tracker before a single `SaveChanges` call, or wrap the multiple saves in an explicit transaction.
- Avoid independent `SaveChanges` calls that can leave the system in a partially committed state.
- If using multiple saves within a transaction, ensure `SaveChanges` failures trigger a rollback and rethrow the exception.
- Use the configured `ExecuteInTransactionAsync` overload with the appropriate isolation level if the operation spans multiple repositories or handlers.
- Do not silently swallow exceptions; propagate them to the global exception handler.
- Ensure transaction scope does not unnecessarily block unrelated operations for long periods.

## Error handling

- Validation failures must return `400 Bad Request` before any transaction begins.
- Authorization failures must return `401 Unauthorized` or `403 Forbidden` before any transaction begins.
- Unexpected persistence failures during the transaction must trigger a full rollback and be logged as errors with a correlation/trace identifier.
- The caller must receive a consistent error response without internal implementation details.
- Deadlock or transient database errors must surface to the caller so that a retry decision can be made at the appropriate layer.

## Idempotency / Retry considerations

- `SportsComplexes` must enforce uniqueness on the natural key or identifier used for the entity (`Id` is generated, but name/city/phone uniqueness should not be relied upon alone for retry safety; the caller should be able to detect that the previous attempt failed and did not commit).
- `ComplexAdministrators` has a unique `(SportsComplexId, UserId)` constraint, preventing duplicate administrator links if a retry incorrectly reaches that point.
- `BusinessHours` has a unique `(SportsComplexId, DayOfWeek)` constraint, preventing duplicate default hours if a retry incorrectly reaches that point.
- Tests must verify that a failed transaction leaves no committed state and that a subsequent retry produces exactly one complete, consistent complex setup.

## Out of scope

- Changes to the public visibility or moderation rules of a complex.
- Changes to the fields, validation rules, or semantics of `SportsComplex` public data.
- Super-admin approval/rejection workflow.
- Asynchronous or background processing of onboarding.
- Business-hours customization beyond the seven default records created during onboarding.
