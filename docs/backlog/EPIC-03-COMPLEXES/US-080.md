# US-080 — View and edit my complex before activation

## Status

Done

## Objective

As a complex administrator, I want to view and edit my complex information regardless of its activation state, so that I can complete the onboarding and prepare the complex before a super administrator moderates it.

## Functional description

This user story enables a complex administrator to access and manage the sports complex they administer even when the complex is in `Pending` status. The public listing and detail endpoints continue to expose only `Active` complexes, but a new administrative read path allows authorized administrators to retrieve and update their own complex in `Pending`, `Active`, or `Inactive` state.

This resolves the cross-story gap where the complex-admin onboarding flow creates a `Pending` complex and redirects the administrator to the admin area, while the existing profile page uses the public active-only endpoint and cannot load the pending complex.

## Acceptance criteria

- [ ] A complex administrator can retrieve the full details of a complex they administer regardless of its `Status`.
- [ ] A complex administrator can edit the public information of a complex they administer when it is `Pending`, `Active`, or `Inactive`.
- [ ] A complex administrator cannot retrieve or edit a complex they do not administer.
- [ ] Public list and detail endpoints continue to return only `Active` complexes.
- [ ] The public endpoint does not accept a parameter to include non-active complexes.
- [ ] The solution works immediately after onboarding, when the user is redirected to the administrative area for a `Pending` complex.
- [ ] A super administrator can still list and manage all complexes through existing moderation endpoints.
- [ ] The response contract for the administrative read is the same as the existing `SportsComplexInfo` contract.
- [ ] Unit, integration, and frontend tests verify the behavior for each status and cross-complex denial.

### Given / When / Then

**Scenario 1: Administrator views their pending complex**

- **Given** a user has completed the complex-admin onboarding and a `Pending` complex was created with that user as its first `ComplexAdministrator`.
- **When** the user navigates to the complex admin area or the complex profile page.
- **Then** the system retrieves the complex through an administrative path that verifies the `ComplexAdministrator` relationship and returns the full complex information, including `Pending` status.

**Scenario 2: Administrator edits their pending complex**

- **Given** a complex administrator is viewing their `Pending` complex.
- **When** the user updates allowed fields such as name, description, address, city, coordinates, phone number, and email.
- **Then** the system validates the input, persists the changes, refreshes `UpdatedAt`, and returns the updated complex information.

**Scenario 3: Non-administrator cannot access another complex**

- **Given** an authenticated user is a `ComplexAdmin` for complex A but not for complex B.
- **When** the user attempts to retrieve or update complex B through the administrative path.
- **Then** the system returns `403 Forbidden`.

**Scenario 4: Public access remains restricted to active complexes**

- **Given** a complex exists in `Pending` or `Inactive` status.
- **When** an unauthenticated or public user calls the public list or detail endpoint.
- **Then** the endpoint does not include or return the non-active complex.

**Scenario 5: Public endpoint ignores status-bypass parameters**

- **Given** a public user calls the public detail or list endpoint with any parameter attempting to include non-active complexes.
- **When** the request is processed.
- **Then** the system ignores the parameter and continues to apply the active-only filter.

## Business rules

1. A user is a complex administrator when an active `ComplexAdministrator` record exists linking that user to the complex.
2. Complex administrators may view and edit the public details of any complex they administer, regardless of `ComplexStatus`.
3. Public endpoints (`GET /api/v1/complexes` and `GET /api/v1/complexes/{id}`) must return only `Active` complexes.
4. The administrative read must be a separate path from the public read and must rely on the `ComplexAdministrator` relationship, not on public status.
5. The `Status` field may be visible to the administrator but is still controlled through the existing status update endpoint (`PATCH /api/v1/complexes/{id}/status`), which is already protected by role and scope.
6. Super administrators retain the ability to list and manage all complexes through existing moderation endpoints; this story does not introduce new moderation logic.
7. The activation state of a complex does not affect the ownership or administration relationship.

## Validations

- Validate the user is authenticated.
- Validate the user has an active `ComplexAdministrator` association for the requested complex.
- Validate the same input rules used for creation when editing public details (name, description, address, city, phone, email, coordinates).
- Return clear, structured error messages for invalid input or unauthorized access.

## Error cases

- Invalid or missing input data returns `400 Bad Request`.
- User is not authenticated returns `401 Unauthorized`.
- User is authenticated but does not administer the complex returns `403 Forbidden`.
- The referenced complex does not exist returns `404 Not Found`.
- A public user attempts to access a non-active complex through the public endpoint returns `404 Not Found`.

## Security considerations

- Authenticate and authorize every mutating request.
- Do not expose the `Pending` or `Inactive` status of a complex to public callers.
- Do not add query parameters to public endpoints that could bypass the active-only filter.
- Verify the actor belongs to or administers the affected complex using the persisted `ComplexAdministrator` record.
- Avoid logging sensitive data such as tokens, PII, or internal identifiers.
- Do not rely on JWT complex claims alone; resolve the association from the database on each request.

## API considerations

The implementation must clearly separate the public and administrative concerns:

### Public endpoints

- `GET /api/v1/complexes` — list active complexes with optional search and pagination.
- `GET /api/v1/complexes/{id}` — detail of an active complex.
- No change to active-only filtering; no parameter to include `Pending` or `Inactive` complexes.

### Administrative endpoints

- `GET /api/v1/complexes/{id}/admin` or equivalent authenticated route under the complex-admin authorization policy — returns the full complex details, including `Pending` or `Inactive` status, when the caller is an active `ComplexAdministrator` for that complex.
- `PUT /api/v1/complexes/{id}` remains the existing update endpoint, protected by the `ComplexAdmin` policy, and already validates the `ComplexAdministrator` relationship through the authorization handler. It must accept `Pending` and `Inactive` complexes as well as `Active` ones.

The administrative read should return the same `SportsComplexInfo` contract as the public detail endpoint so the frontend can reuse the profile form without mapping differences.

## Technical notes

- `SportsComplex` entity: `Id`, `Name`, `Description`, `Address`, `City`, `Latitude`, `Longitude`, `PhoneNumber`, `Email`, `Status`, `AllowUserRecurringReservations`, `CreatedAt`, `UpdatedAt`.
- `ComplexAdministrator` links user and complex with a role and an active/inactive status.
- Public listing returns only active complexes and public fields.
- The frontend `ComplexProfilePage` should use the administrative read endpoint when the user is in the admin area.
- TanStack Query caches for admin reads should be keyed independently of public reads to avoid leaking `Pending`/`Inactive` data when the user switches contexts.

## Tests required

### Unit

- Administrative query returns the complex when the caller is an active administrator.
- Administrative query returns null/empty when no active `ComplexAdministrator` association exists.
- Update handler allows editing `Pending` and `Inactive` complexes for the administrator.

### Integration

- `GET` administrative path returns `Pending`, `Active`, and `Inactive` complex for the assigned administrator.
- `GET` administrative path for a different complex returns `403`.
- `PUT` administrative update persists changes on a `Pending` complex.
- Public `GET` list/detail continue to exclude `Pending` and `Inactive` complexes.
- Public `GET` ignores any `includePending` or similar bypass parameter.

### E2E

- After complex-admin onboarding, the user is redirected to `/admin/complex/{id}` and the profile page loads the `Pending` complex.
- The user can edit the complex profile while it is `Pending`.
- Public pages do not display the `Pending` complex.

## Out of scope

- Status changes by the administrator beyond the existing activate/deactivate endpoint.
- New fields or capabilities for `SportsComplex` beyond the existing public information.
- Email or notification workflows for moderation.
- Changes to the public active-only listing contract.
