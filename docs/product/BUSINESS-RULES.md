# Business Rules

## Reservations

### Single reservations

- A single reservation belongs to exactly one complex, one court, and one user.
- A reservation has a start and end date/time in UTC.
- A reservation must not overlap with another active reservation on the same court.
- A reservation must not overlap with a `CourtBlock` on the same court.
- For the MVP, user reservations are confirmed immediately because there is no payment.
- Status values: `Pending`, `Confirmed`, `CancelledByUser`, `CancelledByAdmin`, `Completed`, `NoShow`.

### Conflict prevention

- Overlap validation runs in the application layer.
- Validation must be transactional to prevent race conditions.
- A concurrency protection strategy must be used (serializable isolation or advisory locks).
- Integration tests must verify concurrent reservation creation.

### Cancellation

- User cancellation policy is configurable per complex through the admin panel.
- The global `CancellationPolicy` configuration (`MinimumHours = 24`, `AllowUserCancellation = true`) is the fallback for complexes without explicit settings.
- `MinimumHours` defines the minimum notice required for user cancellation.
- `AllowUserCancellation = false` disables user self-cancellation in that complex.
- Administrators can cancel reservations without the same time restriction.
- Every cancellation records actor, timestamp, previous status, and optional reason.

### Recurring reservations

- A recurring reservation is defined by a weekly rule.
- It must include an end date or a maximum number of weeks.
- The system generates individual `Reservation` records for each occurrence.
- Cancelling a single occurrence updates only that record.
- Cancelling the series updates all future occurrences.
- Modifying a rule affects future occurrences only.

## Court and availability

- A court can be associated with one or more sports.
- An active court must have at least one associated sport.
- Availability is defined by `CourtAvailabilityRule` per day of week.
- `SlotDurationMinutes` determines the length of bookable slots.
- A complex may have `BusinessHours` separate from court-specific availability.
- Time slots are generated by intersecting availability rules with business hours, existing reservations, and court blocks.

## Users

- A user must complete their profile (including phone number) before making a reservation.
- Phone format is validated but not verified via SMS/WhatsApp in the MVP.
- A `PhoneVerified` flag is stored for future verification.

## Blocking

### User blocking

- Blocking is scoped to one complex.
- A user blocked in complex A may still use other complexes.
- A blocked user cannot create new reservations in the blocking complex.
- Block records include user, complex, reason, blocking admin, timestamp, optional expiration, and status.

### Time slot blocking

- Administrators can block a court for a time range.
- Block reasons include maintenance, event, internal use, holiday, closure, or other.
- Blocked time slots are not shown as available.
- Blocked time slots do not overlap with active reservations.

## Audit

- Relevant administrative actions are recorded in `AuditLog`.
- Audit log includes actor, complex scope, action, entity type, entity id, timestamp, and optional metadata.
- Audit records are immutable.
